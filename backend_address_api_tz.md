# TL;DR

Нужно реализовать каскадное API выбора адреса для мобильного приложения.

Сценарий:
1. Клиент получает список населенных пунктов.
2. Если выбранный пункт уже имеет `id`, это конечный адрес.
3. Если `id == null`, клиент запрашивает список улиц.
4. Если выбранная улица уже имеет `id`, это конечный адрес.
5. Если `id == null`, клиент запрашивает список домов.
6. Выбранный дом возвращает конечный `address_id`.

Главное правило:
- если у выбранного элемента есть `id`, значит это уже легитимный адрес для использования в `/notifications/history/?address_id=...`
- если `id` нет, значит адрес нужно уточнить следующим выбором

Нужные endpoint-ы:
- `GET /notifications/address-tree/cities/`
- `GET /notifications/address-tree/streets/?city_id=...`
- `GET /notifications/address-tree/buildings/?street_id=...`

Каждый элемент ответа должен иметь поля:
- `id`
- `name`
- `type`
- `full_address`
- `has_children`
- `next_level`

Важно:
- конечный `id` должен быть совместим с уже существующим `GET /notifications/history/`
- нужно поддержать неполные адреса:
  - только населенный пункт
  - населенный пункт + улица
  - населенный пункт + улица + дом

# ТЗ для backend

## Задача

Нужно реализовать API для каскадного выбора адреса в мобильном приложении.

Сценарий клиента:
1. Клиент запрашивает список населенных пунктов.
2. Пользователь выбирает населенный пункт.
3. Сервер сообщает:
   - можно ли уже использовать этот выбор как конечный адрес
   - нужно ли уточнение до улицы
4. Если нужно, клиент запрашивает список улиц выбранного населенного пункта.
5. Пользователь выбирает улицу.
6. Сервер сообщает:
   - можно ли уже использовать эту улицу как конечный адрес
   - нужно ли уточнение до дома
7. Если нужно, клиент запрашивает список домов выбранной улицы.
8. Пользователь выбирает дом и получает конечный `address_id`.

Главное правило:
- если выбранный объект уже содержит валидный `id`, то это уже конечный адрес, и клиент может использовать его для:
  - подписки на push
  - запроса истории уведомлений через `/notifications/history/?address_id=...`
- если `id == null`, значит выбор еще не завершен и нужно запрашивать следующий уровень

Это нужно, потому что адреса могут быть разной глубины:
- только населенный пункт
- населенный пункт + улица
- населенный пункт + улица + дом

## Требование совместимости

- `id` конечного выбранного адреса должен быть тем же `address_id`, который уже используется в `GET /notifications/history/`.

## Предлагаемые endpoint-ы

### 1. `GET /notifications/address-tree/cities/`

Назначение:
- вернуть список населенных пунктов для первого шага выбора

Response 200:

```json
[
  {
    "id": 10,
    "name": "Хутір Зелений",
    "type": "settlement",
    "full_address": "Хутір Зелений",
    "has_children": false,
    "next_level": null
  },
  {
    "id": null,
    "name": "Тростянець",
    "type": "city",
    "full_address": "Тростянець",
    "has_children": true,
    "next_level": "street"
  },
  {
    "id": null,
    "name": "Боромля",
    "type": "village",
    "full_address": "Боромля",
    "has_children": true,
    "next_level": "street"
  }
]
```

Логика:
- если `id != null`, это уже конечный адрес
- если `id == null`, нужно идти на следующий уровень
- `next_level`:
  - `street`
  - `building`
  - `null`

### 2. `GET /notifications/address-tree/streets/?city_id=...`

Назначение:
- вернуть список улиц для выбранного населенного пункта

Параметры:
- `city_id` — обязательный, идентификатор выбранного населенного пункта или узла верхнего уровня

Response 200:

```json
[
  {
    "id": 25,
    "name": "Центральна",
    "type": "street",
    "full_address": "Боромля, вул. Центральна",
    "has_children": false,
    "next_level": null
  },
  {
    "id": null,
    "name": "Шевченка",
    "type": "street",
    "full_address": "Тростянець, вул. Шевченка",
    "has_children": true,
    "next_level": "building"
  }
]
```

Логика:
- если у улицы уже есть `id`, она является конечным адресом
- если `id == null`, нужно выбирать дом

### 3. `GET /notifications/address-tree/buildings/?street_id=...`

Назначение:
- вернуть список домов для выбранной улицы

Параметры:
- `street_id` — обязательный, идентификатор узла улицы

Response 200:

```json
[
  {
    "id": 101,
    "name": "12",
    "type": "building",
    "full_address": "Тростянець, вул. Шевченка, 12",
    "has_children": false,
    "next_level": null
  },
  {
    "id": 102,
    "name": "14",
    "type": "building",
    "full_address": "Тростянець, вул. Шевченка, 14",
    "has_children": false,
    "next_level": null
  }
]
```

## Единый формат элемента

Каждый элемент списка на любом уровне должен иметь одинаковую структуру:

```json
{
  "id": 102,
  "name": "14",
  "type": "building",
  "full_address": "Тростянець, вул. Шевченка, 14",
  "has_children": false,
  "next_level": null
}
```

Поля:
- `id` — конечный `address_id`, если выбор на этом уровне уже легитимен; иначе `null`
- `name` — короткое отображаемое имя
- `type` — `settlement`, `city`, `village`, `street`, `building`, optional по внутренней модели
- `full_address` — строка для UI
- `has_children` — есть ли следующий уровень уточнения
- `next_level` — `street`, `building` или `null`

## Ключевая бизнес-логика

Нужно поддержать такие варианты:
1. Населенный пункт сам по себе является адресом.
   Пример: хутор или село без улиц и домов.
   Тогда в `/cities/` объект возвращается с `id != null`, `has_children = false`.

2. Населенный пункт требует выбора улицы.
   Тогда в `/cities/` объект возвращается с `id = null`, `has_children = true`, `next_level = "street"`.

3. Улица сама по себе является адресом.
   Пример: в селе уведомления привязаны к улице без номера дома.
   Тогда в `/streets/` объект возвращается с `id != null`, `has_children = false`.

4. Улица требует выбора дома.
   Тогда в `/streets/` объект возвращается с `id = null`, `has_children = true`, `next_level = "building"`.

5. Дом всегда конечный адрес.
   Тогда в `/buildings/` всегда `id != null`, `has_children = false`.

## Ошибки

- `400` если отсутствует обязательный параметр

```json
{
  "error": "city_id required"
}
```

```json
{
  "error": "street_id required"
}
```

- `400` если параметр невалиден

```json
{
  "error": "invalid city_id"
}
```

```json
{
  "error": "invalid street_id"
}
```

- `404` если дочерние элементы не найдены

```json
{
  "error": "streets not found"
}
```

```json
{
  "error": "buildings not found"
}
```

## Требования к данным

- Нужно использовать ту же сущность адреса, которая уже участвует в `/notifications/history/`.
- Нельзя генерировать отдельные временные id для клиента.
- Конечный `id` должен быть напрямую пригоден для:

```text
GET /notifications/history/?address_id=<id>&firebase_token=<token>
```
